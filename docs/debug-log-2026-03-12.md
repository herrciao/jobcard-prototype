# 除錯紀錄 — 2026-03-12

## 1. 日期格式不統一

**現象**：改車單列表顯示 `3/12/2026`（美式），檔名卻是 `2026-03-12-01`（年月日），兩邊格式混亂。

**原因**：建立改車單時用了 `new Date().toLocaleDateString('en-US')`，輸出 MM/DD/YYYY。

**修復**：統一使用自訂 `formatDate()` 輸出 `YYYY/MM/DD`，並在日期旁加上 `(YYYY/MM/DD)` 提示。

**學到的事**：日期格式要在專案初期就統一定義，不要依賴瀏覽器的 `toLocaleDateString`，因為不同地區輸出不同。

## 2. Foreign Key 約束錯誤（job_cards_user_id_fkey）

**現象**：點新增改車單，彈出 `insert or update on table "job_cards" violates foreign key constraint "job_cards_user_id_fkey"`。

**原因**：`profiles` 表裡沒有當前用戶的資料。`signIn` 回調裡的 `upsert` 靜默失敗（沒檢查錯誤），導致 profile 沒寫入，後續 insert job_card 時外鍵找不到對應的 user_id。

**修復**：
- 在 `signIn` 回調加上 error 檢查和 console.error
- 在 API route 的 `ensureProfile` 加上錯誤回傳，失敗時不繼續建卡

**學到的事**：Supabase 的 `upsert`/`insert` 不會自動拋錯，必須手動檢查 `{ error }` 回傳值。任何資料庫操作都不要假設一定成功。

## 3. Email 衝突導致 Profile ID 更新失敗

**現象**：彈出 `update-by-email: update or delete on table "profiles" violates foreign key constraint "job_cards_user_id_fkey" on table "job_cards" (23503)`。

**原因**：
- `profiles` 表裡已有一筆舊資料（測試時留下的），email 相同但 ID 不同
- 舊 ID 下面掛了 job_cards
- 試圖把舊 profile 的 primary key (id) 改成新值，被外鍵擋住（ON DELETE CASCADE 但沒有 ON UPDATE CASCADE）

**修復**：改用「不改 ID」策略 —— 如果 email 已存在，直接沿用舊 profile 的 ID，不嘗試修改 primary key。抽出共用的 `resolveUserId()` 函數：
1. 先用 session ID 查 → 找到就用
2. 找不到就用 email 查 → 找到就沿用舊 ID
3. 都沒有才建新 profile

**學到的事**：
- PostgreSQL 的 primary key 被其他表 FK 參照時，不能隨意更新
- ON DELETE CASCADE ≠ ON UPDATE CASCADE，兩者要分開設定
- 使用者的 OAuth provider ID 在不同情境下可能不同（測試 vs 正式、不同 session），用 email 做 fallback 查詢更穩健

## 4. Google OAuth 403 disallowed_useragent

**現象**：朋友點連結登入時出現 `403: disallowed_useragent`，即使複製到 Safari 也可能失敗。

**原因**：
- 從 LINE / Messenger / Instagram 等 App 內開連結，使用的是嵌入式瀏覽器（WebView）
- Google 禁止在 WebView 中進行 OAuth 登入
- 即使複製到 Safari，如果 OAuth 應用還在「測試」模式，非測試用戶也無法登入

**修復**：
- 到 Google Cloud Console → OAuth consent screen → 目標對象 → 點「發布應用程式」
- 或在「測試使用者」區塊手動加入朋友的 Gmail

**學到的事**：
- Google OAuth 應用預設是「測試」模式，只有加入的測試用戶能登入
- 正式上線前一定要「發布應用程式」
- 只用 email + profile 基本 scope 的話，發布不需要 Google 審核
- 要提醒用戶用一般瀏覽器（Chrome/Safari）開啟，不要從 App 內建瀏覽器登入

## 架構層面的教訓

| 主題 | 教訓 |
|------|------|
| 錯誤處理 | Supabase 操作一定要檢查 `{ error }`，不要假設成功 |
| 身份識別 | 不要只靠 OAuth provider ID，email 是更穩定的識別方式 |
| Primary Key | 被 FK 參照的 PK 不要隨意更新，設計時考慮 ON UPDATE CASCADE 或避免改 PK |
| 日期格式 | 專案初期就統一定義，不依賴 `toLocaleDateString` |
| OAuth 發布 | 開發完記得從「測試」改成「正式發布」 |
| 除錯技巧 | 把實際錯誤訊息傳到前端顯示，比通用錯誤訊息更容易定位問題 |
